# ticket-brief

한 작업의 요구사항과 연결 자료를 읽어 하나의 브리프 문서로 정리한다.
가정 없이 원천 자료를 수집하는 것이 목적이다 — 분석·구현은 하지 않는다.

## When to Activate

- SDD 워크플로우의 **Request 단계** — 새 작업을 시작해 요구사항을 모을 때
- 흩어진 요구사항을 하나로 정리하고 싶을 때 (단독 사용 가능)

## Input

- 작업 설명 (사용자가 직접 준다). 없으면 사용자에게 묻는다.
- (선택) GitHub 이슈 번호 — 있으면 `github` MCP 또는 `gh issue view`로 본문·완료조건을 읽는다.
- (선택) Figma URL — `figma` MCP로 디자인 스펙을 확인하거나 URL만 수집한다.
- 출력 경로 (없으면 `{tracking.dir}/{슬러그}/request.md`, 기본 `.tracking/...`)

## Procedure

### 1. 요구사항 수집

사용자 설명에서 무엇을 해야 하는지, 왜 하는지, 완료 조건이 무엇인지를 추출한다.
GitHub 이슈가 주어졌으면 제목·본문·라벨(타입 힌트)·완료조건을 읽는다.

### 2. 연결 자료 확인

- **GitHub 이슈**: 있으면 이슈 URL·번호를 원천 링크로 남긴다.
- **Figma**: URL을 수집한다. 필요하면 `figma` MCP로 프레임/화면 구성을 확인한다.

필요해 보이는데 자료가 없으면 **사용자에게 묻는다.** 추측하지 않는다.

### 3. 출력 경로 결정

출력 경로가 주어지지 않았으면 `.tracking/{슬러그}/request.md`.
- 슬러그는 제목 기반 영문 kebab-case로 제안 → **사용자에게 확인받는다.** (예: `social-login`)

### 4. 문서 작성

이 스킬의 `template.md` 형식을 따른다.
frontmatter의 `type`·`title`은 반드시 채운다. (`type`: feat/fix/refactor/chore 등)
해당 자료가 없는 섹션은 비워두지 말고 `(없음)`으로 명시한다.

## Done

- 출력 파일이 생성됨
- 요구사항·완료조건·연결 자료가 빠짐없이 정리됨

작성 후 사용자에게 요약을 보여준다. 이때 `(없음)`으로 남은 항목이나 모호한 요구사항을
**구멍으로 함께 짚어준다** — 막아서 묻지 말고, 사람이 검토 단계에서 판단하도록 드러내기만 한다.
